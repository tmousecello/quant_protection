# Stage 3 結果誠實性審計(對抗性)

> 角色設定:你不是來確認結果的,你是**對抗性審計者**——任務是**試圖證明 Stage 3 的結果是量測管線的 artifact 而非機制的真實效果**。你失敗了(所有攻擊都被證據擋下),結果才算通過審計。發現任何問題,據實回報,不做任何修飾;寧可誤報也不要漏報。
>
> 動機:Stage 3 的數字「太乾淨」(recall 200 ticks 恰等 clean、G 逐點相等、驗證偏差僅門檻 1/9)。乾淨有兩種來源:機制真的好,或量測在某處短路(量到自己的假設)。本專案歷史上每一輪都抓到過結構性問題(單位誤讀 100×、Option A 二次注入、run 3 構造性零、XOR lane aliasing)——先假設這輪也有,去找。

---

## 審計原則

1. **只讀凍結產物與碼**,不重跑不改碼(除非為了驗證而需要極小的離線重算——用產物數據算,不碰工作站)。
2. 每一項檢查的結論必須是三者之一:**CLEAN**(有具體證據排除嫌疑)/ **ARTIFACT**(找到問題,附機制)/ **UNVERIFIABLE**(現有產物無法排除——這也是發現,要列出補什麼才能排除)。
3. 「測試通過」不是證據——**gate 本身可能是套套邏輯**(斷言把結果釘死成必然)。要查的是 gate 檢查的東西與聲稱的結論之間是否真有推理距離。
4. 特別警惕三種模式:(a) **保護路徑量到自己**(注入與量測共用同一份資料/同一段碼,保護機制「修復」的其實是量測的輸入);(b) **構造性成功**(結果由實驗設計保證,與機制好壞無關——run 3 的先例);(c) **選擇效應**(失敗的 run 沒進報告)。

## 嫌疑清單(按可疑度排序,逐項查)

### 嫌疑 1【最高】:#1 的 recall「恰等於」clean——注入是否真的碰到了查詢路徑?

200 ticks recall 唯一 distinct 值 = 0.98376。機制解釋(每 tick 修復在查詢前完成)是可能的,但另一個解釋是**查詢用的 rotation 根本不是被注入的那份**(例如:C++ 查詢端持有自己的 rotation 副本/在 index load 時已拷貝,Python 端注入的 buf 與 C++ 實際使用的記憶體是兩份)。若如此,整個 E5 懸崖層量的是空氣。

**證偽探針**:
- 追碼:注入寫入的 rotation 位址/檔案,與 C++ 查詢實際讀取的 rotation,是否同一份?(關鍵:E5 的查詢是每 tick 重新 load index 檔?還是常駐 process?注入是打檔案還是打記憶體?)
- **交叉證據(最強)**:run 2(無防護)與 run 3/#1 用**同一注入管線**——run 2 的 recall 確實崩了(0.423),證明注入管線本身能影響查詢。確認 run 2 與 #1 的注入→查詢路徑**完全相同、唯一差異是 scrub 開關**。若兩者路徑有任何不同(不同腳本、不同 load 時機),嫌疑不排除。
- 檢查 #1 的 records:tick 77/79/94/137 的投票失敗事件,對應 tick 的注入 bits 是否真的落在會觸發 ≥2 複本同位的位置?(從 per-tick 注入記錄離線重算,驗證 4 次觸發不是隨機噪音而是真實雙擊。)

### 嫌疑 2:#1 的修復時序——scrub 是否在「recall 量測之前」偷跑?

若每 tick 的順序是「注入 → scrub → 量 recall」,那 recall 全平只證明「scrub 在量測前修好了」——這是機制設計的一部分,OK;但若順序是「注入 → 量 recall → scrub」而 recall 仍全平,那就矛盾(注入後未修的損傷應該影響該 tick 的 recall,除非注入沒生效 → 回到嫌疑 1)。反之,若聲稱的語意是「查詢期間持續 scrub」但實作是「量測前一次性修復」,則「每查詢修」的論文敘述與實作不符。

**證偽探針**:讀 timeline 迴圈的實際順序(§1 契約:inject_step → search_with_recovery → measure → scrub_if_due);比對 #1 的實作與 run 2 的迴圈——run 2 tick-0 就崩,代表 run 2 的量測發生在注入後、無修復;#1 若同一迴圈只多了 scrub,則順序一致、結論成立。任何迴圈順序差異都要標出。

### 嫌疑 3:「clean 源」是否被腐蝕流豁免——這是機制假設還是實驗捷徑?

觸發式重載從索引檔讀 clean rotation。**檔案不被注入是威脅模型的一部分(持久儲存不受 DRAM 錯誤影響)——這是合法假設**;但要驗證:(a) 實作確實從檔案讀,而非從某個 DRAM 中的 clean 快取(指示明文禁止,查有沒有偷快取);(b) 若 E5 的注入是打檔案(而非記憶體),那 clean 源和被注入對象是同一個檔案 → 重載讀到的是腐蝕值,結果不可能全平 → recall 全平反而證明有第二份未腐蝕來源 → 追出它是什麼、是否合法。

**證偽探針**:追 `_scrub_cliff` 重載的資料來源(檔案 offset 讀取?哪個檔?);比對注入目標(檔 or 記憶體 buf);確認兩者的關係與論文敘述(「錨定持久 clean 源」)一致。

### 嫌疑 4:#3 驗證點的循環論證——合成與實測是否共用同一數據源?

偏差 0.000186 小得可疑。若「合成預測」是從 expb 容忍曲線內插、而「實測」是**重新在同一批 expb records 上讀值**(而非新跑),那偏差小是套套邏輯。報告說驗證點是工作站新實測——查證。

**證偽探針**:fstar_check 的產物 timestamp / provenance 是否為 07-09 新 run(而非引用 07-08 的 expb);其注入 seed / f 值與 expb 原 sweep 是否不同(同 f 但新 seed 才是獨立驗證;同 seed 同 f 就是重讀);(c) 懸崖點 Δ=0.0 尤其可疑——「6-bit 決定性重現」若是同 seed 同 bits,Δ=0.0 是必然(決定性系統),它驗證的是**重現性**而非**合成正確性**,報告把它列為驗證 gate 的措辭是否過強?

### 嫌疑 5:G 的「逐點相等」——報告已自認構造性,查它的定位是否誠實傳播

`g_detection_summary.json` 已註記構造性(分子由斷言釘死)。查:(a) 論文草稿/圖 caption 引用 G 時是否保留了這個限定,還是把對角圖當成「偵測準確率的實驗發現」在賣;(b) 那個斷言(`crc_fail==n_elements`)若失敗會發生什麼——run 會 abort(誠實)還是被 except 吞掉(選擇效應)?

### 嫌疑 6:#2 的選擇效應與模型吻合度

- 30 個 seed 是**全部跑的 seed**(1000–1029 連號)還是挑過的?查批次腳本的 seed 生成——連號 + 全數進報告 = CLEAN;任何缺號要解釋。
- censored seed 1005 在 mean 的處理:報告已標「mean 25.4 為下偏」——查 median/IQR 的引用是否確實不受影響(censoring 在 150 > median 21,是);但**幾何模型的 p=0.0384 是怎麼估的**?若 p 是從同一批 30 seeds 的失敗數據擬合出來的,那「實測與模型吻合」是部分循環;若 p 是從複本淨損 bits 的獨立物理量推的(報告聲稱如此),則吻合是真驗證。追這條推導。

### 嫌疑 7:全綠 log 的反面——有沒有沒進報告的 run?

- 工作站 artifacts 目錄與 git 歷史裡,有沒有 Stage 3 期間產生、但未被報告引用的 run 產物(失敗的、重跑的、參數不同的)?每一份都要問:為什麼沒進報告?(合法理由:smoke、除錯;不合法:結果不好看。)
- `run_stage3_x86.sh` 是「任一 gate fail 即中止」——查它在 07-09 之前有沒有中止過的執行痕跡(log 目錄的其他 timestamp),若有,中止原因與後續修改是什麼?修改是修 bug(合法)還是調參數直到過(p-hacking 味)?

### 嫌疑 8:anchor 保底 19/0——它真的在工作嗎?

19 次檢查 0 次 mismatch 符合預期(盲區機率極低),但也與「anchor check 根本沒在比對」(恆回傳 OK)不可區分。**證偽探針**:stub 測試裡有一條「構造同位同值雙擊 → 保底抓到」——確認這條測試存在、真的構造了盲區情境、且在目前的碼上通過。若測試存在且過,19/0 可信。

## 交付格式

對每個嫌疑:結論(CLEAN / ARTIFACT / UNVERIFIABLE)+ 證據(檔案:行號 / 產物欄位 / 離線重算數字)+ 若 ARTIFACT:影響範圍(哪些結論失效)與最小修復;若 UNVERIFIABLE:需要補什麼(限文字/解析/既有產物,凍結不解)。

最後給一個總評:**Stage 3 的三個 headline 主張(自我 scrub 可無限續命、首失敗 median ~21、偵測零成本吐出決策變數)各自站在什麼證據強度上**——直接量測 / 構造性 / 推導 / 未驗證,逐一標明。這個分級會直接進論文的措辭校準。

## 邊界
- 不重跑實驗、不改機制碼(凍結);發現 ARTIFACT 也先報告,修復方案另議。
- 不確定就標 UNVERIFIABLE,不要腦補成 CLEAN。
- 審計報告本身也要誠實:你若無法從產物排除某嫌疑,說出來,即使那會讓結果難看。
